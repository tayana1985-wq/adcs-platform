# ADCS / KCSL Brain · Спецификация рассуждения

**Статус:** ПРОЕКТ · не утверждён
**Версия:** 0.1 · 2026-09-29
**Предмет:** что Brain считает → как обнаруживает разрыв → как формирует гипотезу → как её проверяет

> Brain — не «умный отчёт». Brain — машина перехода от доказательства к
> проверяемому предположению и обратно к доказательству.

---

## 0. Принципы

| № | Принцип | Что это значит на практике |
|---|---|---|
| P1 | Brain считает только из фактов | Любое число выводится из записей Registry / Pulse / Audit / Participation Evidence / Closed Loop. Brain не порождает факты. |
| P2 | `NO_VERIFIED_DATA ≠ 0` | Отсутствие данных никогда не превращается в ноль — ни при хранении, ни при расчёте, ни при показе. |
| P3 | Гипотеза ≠ факт | Любое объяснение имеет статус и уровень доказанности. Причина не называется до проверки. |
| P4 | Нет единого балла | Никакого «KCSL Score». Brain показывает структуру доказательств по контурам. |
| P5 | Критерий успеха — до проверки | Что считать подтверждением, записывается до получения результата (предрегистрация). |
| P6 | История не переписывается | Журнал рассуждения только дописывается. Отвергнутые и неопределённые гипотезы хранятся наравне с подтверждёнными. |
| P7 | Вклад, а не причина | Для внешних событий (Almaty 2027) Brain говорит о вкладе и совпадении во времени, а не о причинности, если нет сравнительной группы. |

## 1. Архитектура

```
REGISTRY                      что известно
   ↓
BRAIN · FACT ENGINE           что можно математически вывести
   ↓
BRAIN · SIGNAL ENGINE         где изменение / аномалия / разрыв
   ↓
BRAIN · HYPOTHESIS ENGINE     какие существуют объяснения
   ↓
BRAIN · TEST ENGINE           какие данные и какой дизайн нужны для проверки
   ↓
COMPANY ACTION                что компания решила изменить  (решает человек)
   ↓
CLOSED LOOP                   повторный замер
   ↓
BRAIN · RESULT                что изменилось после действия → новый FACT
```

Цепочка объектов:

```
FACT → SIGNAL → GAP/DIFFERENCE/CHANGE → HYPOTHESIS → TEST → RESULT → ACTION → SECOND MEASUREMENT
```

Разделение ответственности:

| Слой | Может | Не может |
|---|---|---|
| Fact Engine | считать, агрегировать, сравнивать | интерпретировать |
| Signal Engine | отмечать разрыв, различие, изменение, пробел | объяснять |
| Hypothesis Engine | предлагать объяснения со статусом `PROPOSED` | присваивать `SUPPORTED` |
| Test Engine | описывать дизайн проверки, считать результат по заранее записанному критерию | менять критерий после результата |
| Человек | утверждать тест, действие, пороги | выдавать стендовые данные за реальные |

## 2. Состояние данных

### 2.1 Статус каждой ячейки

Каждое значение, которое хранит или выводит Brain, несёт один статус:

| Статус | Смысл | Пример |
|---|---|---|
| `VERIFIED` | Значение подтверждено источником | 1 100 участников по журналу посещений |
| `ZERO_VERIFIED` | Подтверждённый ноль: учёт вёлся, событий не было | 0 возвратов при полном журнале |
| `PARTIAL` | Учёт есть, но не по всей совокупности; известно покрытие | журнал по 4 из 7 подразделений, покрытие 61% |
| `NO_VERIFIED_DATA` | Учёта нет или он не подтверждён | возврат участников не фиксировался |
| `NOT_COMPARABLE` | Значение есть, но с другим определением / периодом / совокупностью | «активность» в Pulse ≠ «участие» в журнале |

### 2.2 Правила распространения

| Операция | Результат |
|---|---|
| `VERIFIED` ⊕ `VERIFIED` | `VERIFIED` |
| `VERIFIED` ⊕ `ZERO_VERIFIED` | `VERIFIED` |
| сумма, где хотя бы одно слагаемое `NO_VERIFIED_DATA` | `PARTIAL` с пометкой «не менее X»; не точное X |
| доля, где знаменатель `NO_VERIFIED_DATA` | `NO_VERIFIED_DATA` |
| разность между `NOT_COMPARABLE` величинами | не вычисляется |
| среднее по подразделениям с разным покрытием | вычисляется только по покрытым; покрытие показывается рядом |

Запрещено: подставлять 0, среднее по компании, прошлое значение или
экстраполяцию вместо `NO_VERIFIED_DATA` без явной пометки `IMPUTED` и
отдельного утверждения человеком.

### 2.3 Происхождение

Каждое значение несёт пометку происхождения, и она **наследуется всеми
производными** (сводами, срезами, графиками, разрывами):

`REAL` · `SYNTHETIC_FIXTURE` · `IMPUTED` · `SELF_REPORTED` · `RECORDED`

Производная от `SYNTHETIC_FIXTURE` не может показываться как находка о компании.

## 3. Fact Engine · семь вычислительных контуров

| Контур | Что считает | Входы | Основные выходы |
|---|---|---|---|
| **Evidence** | сколько подтверждённых фактов и где пробелы | все источники | матрица «контур × подразделение × статус», покрытие, список `NO_VERIFIED_DATA` |
| **Programme Chain** | СДЕЛАЛА → ОТКРЫЛА → ПОДТВЕРДИЛА → ИЗМЕРИЛА → УСИЛИЛА | Registry, Audit | этап каждой программы, чем подтверждён каждый этап |
| **Human Funnel** | Сказал → Сделал → Дошёл → Вернулся → Сохранил | Pulse, Participation Evidence | численности этапов, переходы, тип связи этапов (§4) |
| **Participation** | участники, повторное участие, регулярность | Participation Evidence | уникальные участники, частота, доля регулярных, распределения |
| **Closed Loop** | Measurement №1 → действия → Measurement №2 | Pulse, Participation, Company Action | изменение по каждому показателю, действия между замерами |
| **CORE** | BUSINESS / DEVELOPMENT / RELIABILITY / PEOPLE / SOCIETY / SPORT | все | покрытие и статус доказательств по каждому CORE, **без свёртки в балл** |
| **Almaty 2027 Impact** | сейчас → цель → путь года → Игры → после Игр | Registry, Closed Loop | траектория показателей относительно цели; вклад, не причинность (P7) |

### 3.1 Что Fact Engine выводит

- абсолютные числа на каждом этапе и переходы между этапами;
- доли перехода с указанием знаменателя;
- возвраты и повторное участие;
- изменение Measurement №1 → №2 (абсолютное и относительное) с интервалом неопределённости, если данные выборочные;
- распределения по подразделениям / ролям / видам спорта / сменности;
- покрытие каждого CORE и полноту evidence.

### 3.2 Минимальный размер группы

Срез не показывается, если в нём меньше **`MIN_CELL_N`** человек (объявлено: 10,
не утверждено). Причины две: устойчивость оценки и защита от повторной
идентификации. Вместо значения — `SUPPRESSED_SMALL_CELL`.

## 4. Сопоставимость этапов воронки

Разрыв между этапами вычисляется, только если этапы сопоставимы. Каждый переход
несёт тип связи:

| Тип | Условие | Что можно сказать |
|---|---|---|
| `LINKED` | этапы связаны по одному человеку (псевдоним) | «из 2 400 заявивших 1 100 дошли; 1 300 не дошли» |
| `AGGREGATE` | одна совокупность, один период, одно определение, но связи по человеку нет | «заявивших ≈ 2 400 (оценка), участвовавших 1 100; разница по итогам, не по людям» |
| `NOT_COMPARABLE` | разные совокупности / периоды / определения | разрыв не вычисляется; создаётся Evidence Request |

Дополнительно:

- **Выборочный этап** (Pulse) — это оценка с интервалом, а не счёт. Разрыв,
  построенный на ней, тоже несёт интервал.
- **Самоотчёт** (`SELF_REPORTED`) и **учёт** (`RECORDED`) на разных этапах
  указываются явно: часть разрыва может быть разницей между словами и учётом,
  а не потерей людей.

## 5. Signal Engine

Сигнал — это зафиксированное наблюдение без объяснения.

| Тип сигнала | Когда возникает | Пример формулировки |
|---|---|---|
| `GAP` | потеря между этапами воронки или цепочки | «Между намерением и участием не перешли 1 300 человек (`LINKED`).» |
| `DIFFERENCE` | различие между подразделениями / ролями при одной программе | «Вернулись: Алматы 320 из 890, Астана 91 из 610.» |
| `CHANGE` | различие между Measurement №1 и №2 | «Регулярно занимаются: 620 → 810.» |
| `EVIDENCE_GAP` | показатель нельзя установить | «RETURN — NO_VERIFIED_DATA.» |

Правила:

1. Сигнал `DIFFERENCE` и `CHANGE` создаётся только если различие превышает
   объявленный порог материальности **и** интервал неопределённости его не накрывает.
2. При переборе многих срезов применяется поправка на множественность
   (правило Холма, как в существующем Brain). Число проверенных срезов
   записывается в сигнал.
3. Сигнал всегда содержит знаменатели, а не только доли.

## 6. Объекты рассуждения

### 6.1 Гипотеза (три типа)

| Тип | Вопрос | Опирается на сигнал |
|---|---|---|
| `GAP_HYPOTHESIS` | где и почему теряется человек | `GAP` |
| `DIFFERENCE_HYPOTHESIS` | почему при одной программе результаты разные | `DIFFERENCE` |
| `CHANGE_HYPOTHESIS` | что из произошедшего между замерами связано с изменением | `CHANGE` |

### 6.2 Запрос доказательств — не гипотеза

`EVIDENCE_REQUEST` создаётся из сигнала `EVIDENCE_GAP` или из перехода
`NOT_COMPARABLE`. Он не имеет статусов SUPPORTED / NOT SUPPORTED.

Формулировка:
> «Мы не можем установить возврат участников. Для проверки нужны: журнал
> посещений с идентификатором участника за 2 периода; определение возврата;
> покрытие не ниже 80% подразделений.»

Статусы: `OPEN` → `DATA_REQUESTED` → `DATA_RECEIVED` → `CLOSED` / `NOT_OBTAINABLE`.

### 6.3 План проверки — не гипотеза

`TEST_DESIGN` (бывший «intervention hypothesis») описывает, **как** проверить
гипотезу: какое действие, где, с чем сравнивать, какой критерий успеха.
Действие утверждает человек.

### 6.4 Связи

```
SIGNAL ──1:N──> HYPOTHESIS ──1:N──> TEST_DESIGN ──1:1──> RESULT
   │                 │
   └──> EVIDENCE_REQUEST <──┘   (гипотеза может породить запрос данных)
RESULT ──> новый FACT ──> новый SIGNAL (следующий вопрос)
```

## 7. Жизненный цикл гипотезы

```
PROPOSED ──> TESTING ──> SUPPORTED
    │           │   ├──> NOT_SUPPORTED
    │           │   └──> INCONCLUSIVE
    │           └──> ABANDONED   (тест не выполнен; причина обязательна)
    └──> WITHDRAWN               (сигнал оказался артефактом данных)
```

| Переход | Условие |
|---|---|
| PROPOSED → TESTING | есть утверждённый `TEST_DESIGN` с записанным критерием успеха |
| TESTING → SUPPORTED | результат удовлетворяет критерию, записанному до теста |
| TESTING → NOT_SUPPORTED | результат противоречит критерию |
| TESTING → INCONCLUSIVE | данных недостаточно, интервал слишком широк, или дизайн не позволяет отделить эффект |
| любой → WITHDRAWN | исходный сигнал пересчитан и исчез (например, этапы оказались `NOT_COMPARABLE`) |

Запрещено: переводить в `SUPPORTED` без теста; менять критерий после получения
результата; удалять гипотезу из журнала.

## 8. Уровень доказанности

Вместо «уверенность 87%» — уровень с явными правилами:

| Уровень | Правило присвоения |
|---|---|
| `NONE` | гипотеза предложена, опор нет, кроме самого сигнала |
| `LIMITED` | одно наблюдение или одна связь (корреляция) в одном срезе |
| `MODERATE` | повторяется в нескольких подразделениях или двух замерах с поправкой на множественность; **или** предрегистрированный тест со сравнительной группой, но по одному подразделению на группу |
| `STRONG` | предрегистрированный тест со сравнительной группой, эффект не ниже порога, интервал не накрывает ноль, **и** ≥ 2 подразделений на группу, либо случайное распределение, либо успешное повторение |

Ограничение дизайна: тест «до/после» **без сравнительной группы** не может
дать уровень выше `LIMITED` и статус выше `INCONCLUSIVE`, каким бы большим ни
был прирост. Рост мог дать сезон, внешнее событие, возврат к среднему или
само внимание к группе.

## 9. Test Engine

### 9.1 Что записывается до теста

| Поле | Пример |
|---|---|
| гипотеза | H-014 |
| действие | два дополнительных вечерних слота |
| опытная когорта | подразделение X |
| сравнительная когорта | подразделение Y (сопоставимое по численности и сменности, действия нет) |
| показатель | уникальные участники за 8 недель |
| исходные значения | X: 146 · Y: 158 (Measurement №1) |
| минимальный значимый эффект | разница приростов X и Y ≥ +20 человек |
| критерий SUPPORTED | разница приростов ≥ +20 и интервал 95% не накрывает 0 |
| критерий NOT_SUPPORTED | интервал 95% накрывает 0 и верхняя граница < +20 |
| иначе | INCONCLUSIVE |
| период | 8 недель · даты |
| кто утвердил | ФИО и роль, дата (не стендовый актор) |

### 9.2 Допустимые дизайны

| Дизайн | Максимальный уровень |
|---|---|
| до/после без сравнения | `LIMITED` / `INCONCLUSIVE` |
| разница приростов (опыт vs сравнение), по одному подразделению | `MODERATE` |
| разница приростов, ≥ 2 подразделений на группу | `STRONG` |
| поэтапное внедрение по подразделениям в случайном порядке | `STRONG` |

### 9.3 Достаточность данных

До теста Brain оценивает, хватит ли численности когорт, чтобы отличить
минимальный эффект от шума (моделирование мощности — тот же аппарат, что
`TieAwarePower3`). Если не хватит — тест всё равно можно провести, но в
плане заранее записано, что вероятный итог — `INCONCLUSIVE`.

## 10. Журнал рассуждения

Каждая гипотеза хранится как запись, которая только дописывается.

```
H-014
  Тип:               GAP_HYPOTHESIS
  Сигнал:            S-031 · 1 300 человек не перешли от намерения к участию
                     связь этапов: LINKED · происхождение: SELF_REPORTED → RECORDED
  Создана:           30.09.2026 · кем/чем: Hypothesis Engine (кандидат) · утвердил к тесту: <ФИО>
  Формулировка:      одним из факторов может быть доступность времени/расписания
  Основание:         Pulse: временные ограничения указаны чаще прочих (доля, n);
                     подразделения с вечерними слотами: переход выше (доли, n)
  Использовано:      Pulse M1 · Participation Evidence Q3
  Уровень:           LIMITED
  Альтернативы:      H-015 информированность · H-016 удалённость площадки
  Тест:              T-007 · два вечерних слота · X против Y · критерий записан 05.10.2026
  Measurement №1:    X 146 · Y 158
  Measurement №2:    X 213 · Y 171
  Результат:         прирост X +67 · прирост Y +13 · разница +54 · 95% [+3; +105]
  Статус:            SUPPORTED
  Уровень:           MODERATE   (одно подразделение на группу)
  Следующий вопрос:  сохранилась ли активность через 90 дней? → H-014a
                     повторить в двух подразделениях → путь к STRONG
```

Обязательные поля: связь с сигналом, использованные данные с версиями,
альтернативные гипотезы, критерий успеха с датой записи, результат, статус,
уровень, следующий вопрос. Отвергнутые (`NOT_SUPPORTED`) и
неопределённые (`INCONCLUSIVE`) гипотезы остаются в журнале: без них Brain
«учится» только на успехах.

## 11. Чего Brain не говорит никогда

| Нельзя | Можно |
|---|---|
| «Причина — неудобное расписание.» | «Гипотеза H-014: одним из факторов может быть расписание. Статус: не проверено.» |
| «Возврата нет.» | «Возврат установить нельзя: NO_VERIFIED_DATA. Нужны данные: …» |
| «KCSL Score = 72.» | структура доказательств по семи контурам и шести CORE |
| «Уверенность 87%.» | «Уровень доказанности: LIMITED — одно наблюдение.» |
| «После Игр вовлечённость выросла благодаря Играм.» | «Рост совпал по времени с Играми; сравнительной группы нет; причинность не установлена.» |
| «Подтверждено: +67 человек.» (без контроля) | «Прирост +67; без сравнения итог INCONCLUSIVE.» |
| показывать срез из 4 человек | `SUPPRESSED_SMALL_CELL` |

## 12. Связь с существующим Brain (контрольная точка 51509be)

| Нужно здесь | Что уже есть | Что переиспользовать |
|---|---|---|
| статистика связи и мощности | Спирмен со связками, Холм, `TieAwarePower3` | Test Engine §9.3, Signal Engine §5 |
| предрегистрация, критерий до результата | договоры `statcontract`, пороги в `config/thresholds.php` | §9.1 |
| журнал решений, отпечатки, события утверждения | `DECISION_LEDGER`, `br_governance_approval_event`, отпечатки формулировок | §10 |
| разделение стенда и реальности | G91 / G92, пометки `NOT_MEASUREMENT_EQUIVALENT…` | §2.3 — с обязательным наследованием по производным |
| отказ считать при непригодных условиях | патч tap-3.1 (натяжение, невыполнимость) | принцип «отказ лучше ложного числа» во всех контурах |

Не найдено в разборе и требует построения: Registry, Participation Evidence,
Human Funnel, Programme Chain, Closed Loop, CORE, Almaty 2027 Impact,
связь этапов по псевдониму.

Известные ограничения из разбора, которые переходят сюда:

- статистика по communication посчитана на редакции v1, непригодной к предрегистрации;
- утверждения формулировок в стенде подписаны `owner2@test`, не человеком;
- вариант «компания ничего не предлагала» исключает из знаменателя тех, до кого
  не дошла информация, и завышает access (нужен `OFFER_NOT_PERCEIVED`);
- реальных ответов в боевом контуре нет: все текущие числа — `SYNTHETIC_FIXTURE`.

## 14. Порядок внедрения

1. Статусы данных и правила распространения (§2) — без них всё остальное считает неправильно.
2. Определения этапов и ключ связи (D4, D5) — без них Human Funnel не вычисляется.
3. Fact Engine: Evidence и Participation — первые два контура, на которых можно проверить §2.
4. Signal Engine с поправкой на множественность и минимальной группой.
5. Журнал рассуждения (§10) и объекты §6.
6. Test Engine на базе существующего аппарата мощности.
7. Closed Loop, CORE, Almaty 2027 Impact.
